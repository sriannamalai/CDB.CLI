# cdb 1.1: Design

Status: draft, 2026-09-08. Extends the v1 design at
`docs/superpowers/specs/2026-09-08-CdbCliDesign.md`, whose rules still hold and
are not restated: paging never uses `skip`; secrets are never printed, logged,
or accepted as flags; commands return a `Result` and never print to stdout;
every server call takes a `context.Context`; exit codes are 0 success, 1
command error, 2 usage error, 3 connection or auth error, 130 interrupted.
Baseline: `main` at 58f98a1 (v1.0.0).

## 1. Goal

v1.1 closes seven gaps v1 shipped with, each one a thing an operator hits on
the first day: watching a database change, replicating from a machine whose
address the server does not share, backing up deletions, seeing *what* differs
between conflicting revisions, and addressing a partition. It adds one command
(`tail`), one global flag, three command flags, one path-grammar extension, and
a live JWT test. Nothing existing changes shape.

## 2. Decisions

| Decision | Choice |
|---|---|
| Version | 1.1.0. No breaking change to any v1.0 command, flag, path, or config key. |
| New command | `tail` only. |
| Server versions | Unchanged: CouchDB 3.2 through 3.5. |
| Dump format | Header gains `version` (`"1.1"`) and `tombstones`; footer gains `deleted`. Readers accept 1.0 and 1.1. |
| Tombstones | Opt-in (`backup --tombstones`). Default backup output keeps v1.0 shape. |
| Partition documents | `/db/_partition/<key>/<id>` addresses document id `<key>:<id>`. |
| `_changes` and partitions | CouchDB has no partition-scoped `_changes`; `tail` takes a database path only. |
| Replication URL | Per-profile override of the address the server is told to call itself on. Never carries credentials. |
| Diff granularity | Top-level fields, summarised values; `--diff-full` prints whole revisions. |

## 3. Stack changes

None. No dependency is added, removed, or upgraded. The HS256 token the new JWT
test mints comes from `crypto/hmac`, `crypto/sha256` and `encoding/base64` in
about twenty lines; a JWT library is not worth a dependency for that.

## 4. Architecture

Package layout is unchanged. Six packages change.

**`internal/couch`.** `Changes` is re-shaped to take an options struct, because
`tail` needs five parameters `backup` does not. The four-argument form has one
caller (`internal/command/backup.go`), updated to pass `Style: StyleAllDocs`,
so its behaviour is unchanged.

```go
const (
    StyleMainOnly = "main_only" // the zero value of ChangesOptions.Style
    StyleAllDocs  = "all_docs"
)

type ChangesOptions struct {
    Since       string // "" means "0"; "now" is accepted by the server
    Limit       int    // normal feed only; 0 means unbounded
    Style       string // "" means StyleMainOnly
    IncludeDocs bool
    Filter      string // "ddoc/name", or "" for none
    HeartbeatMS int    // continuous feed only; 0 sends no heartbeat
}

func (c *Client) Changes(ctx context.Context, db string, opts ChangesOptions) (ChangesPage, error)
func (c *Client) ChangesFollow(ctx context.Context, db string, opts ChangesOptions, fn func(ChangeRow) error) error
func (c *Client) ReplicationURL() string
```

`ChangeRow` gains `Doc json.RawMessage`, set only when `IncludeDocs` is.
`ChangesFollow` opens `feed=continuous`, reads the body line by line with a
`bufio.Scanner` (max token 4 MiB), calls `fn` for each line that decodes to a
change with an `id`, ignores blank heartbeat lines and the trailing
`{"last_seq":…}` line, and returns when the body ends, when `fn` errors, or
when `ctx` is cancelled. It never retries: the reconnect policy lives in the
command. `couch.Config` gains `ReplicationURL string`, which
`ReplicationEndpoint(db)` uses in place of `c.safe` when set; its credential
handling is unchanged.

**`internal/path`.** `Resolve` learns the partition-scoped forms in §9.
`Target` gains no field: `Partition` is now set on documents, attachments and
views as well as on `KindPartition`. No new exported name.

**`internal/command`.** `Tail()` is a `NeedsClient` command with
`Complete: completePath`, registered in `Default()` after `Query()`. A package
var `backoffSleep func(context.Context, time.Duration) error` holds the
reconnect wait so tests drive the schedule without sleeping. A new file
`internal/command/diff.go` adds:

```go
type ChangeKind int // ChangeAdded, ChangeRemoved, ChangeChanged

// FieldChange is one top-level field that differs between a revision and the
// winner. Winner is empty when the field was added, Other when it was removed;
// both are value summaries, not raw JSON.
type FieldChange struct {
    Field  string
    Kind   ChangeKind
    Winner string
    Other  string
}

// RevisionDiff is one revision compared against the winner. Changes is empty
// for the winner itself.
type RevisionDiff struct {
    Rev     string
    Changes []FieldChange
}

func DiffRevisions(winner, other json.RawMessage, rev string) RevisionDiff
func (d RevisionDiff) Summary() string // one line for the resolve chooser
```

**`internal/render`.** `command.Stream` gains `Live bool`, marking a stream
whose rows must appear as they arrive. `renderStream` today buffers
`streamTableChunk` (200) rows before emitting a table chunk and routes chunks
through the pager; when `Live` is set, in every format, it writes each row to
the session writer as it arrives, flushes, and never pages — so `tail --follow`
prints a change the moment it happens.

**`internal/config`.** `Profile` gains
``ReplicationURL string `koanf:"replication_url"` ``. `Env` gains
`ReplicationURL string`, read from `CDB_REPLICATION_URL` and layered by
`Env.Apply` exactly as `URL` is.

**`internal/shell`.** `CompleteLine` learns the attached-value flag form
(§10.3). No new exported name.

## 5. `tail`

```
tail [path] [--since SEQ] [--limit N] [--follow] [--include-docs]
     [--filter DDOC/NAME] [--heartbeat MS]
```

Reads the `_changes` feed of a database. `path` defaults to the current path
and must resolve to a database. `style` is always `main_only`: one row per
change, not one per leaf revision. (`backup` keeps `all_docs`; different job.)

| Flag | Type | Default | Meaning |
|---|---|---|---|
| `--since` | string | `0`, or `now` when `--follow` is given | Update sequence to start from. |
| `--limit` | int | 25 | Changes to read. `0` reads to the end of the feed. |
| `--follow` | bool | false | Use the continuous feed and keep reading. |
| `--include-docs` | bool | false | Fetch each changed document with the change. |
| `--filter` | string | "" | Design-document filter, as `ddoc/name`. |
| `--heartbeat` | int | 30000 | Milliseconds between server heartbeats. `0` sends none. |

Two defaults depend on `--follow`, so the rules below say "given" to mean the
operator typed the flag (`Invocation.Changed`), not that it holds its default.

**Without `--follow`.** One `feed=normal` request from `--since`, at most
`--limit` changes, returned as a `Stream` with `Live` false, so the paged
renderer handles it exactly as `ls --all` does. When `--limit` is non-zero and
the page came back with exactly that many changes, the result carries the hint
`more changes: tail <path> --since "<last_seq>"`. Exit 0.

**With `--follow`.** The command opens `feed=continuous` from `--since` and
returns a `Live` `Stream`, recording the sequence of every change it emits.
When `ChangesFollow` returns and `ctx` is not cancelled, it reconnects from the
last recorded sequence — or from `--since` if nothing has been seen yet — after
a backoff of 1s, 2s, 4s, 8s, 16s, then 30s for every attempt after that; the
backoff resets to 1s as soon as one change is received. Each reconnect writes
one stderr line: `Lost the changes feed for "mydb"; reconnecting from <seq> in
<n>s.` Retries are unbounded — a tail is meant to be left running. A reconnect
follows a transport error, an end of body, or a 5xx only; a 4xx (database
deleted, token expired) is returned as the mapped `couch.Error` and ends the
command.

**Interruption.** Ctrl-C cancels the session context; `ChangesFollow` returns
`ctx.Err()`, `Next` hands it to the renderer, and the existing mapping applies:
the one-shot front-end prints nothing and exits 130, the shell prints nothing
and returns to the prompt.

**Columns.** `seq`, `id`, `rev`, `deleted`, and — with `--include-docs` —
`doc`, holding the same 80-rune summary `find` uses. `deleted` renders
`true`/`false`. `Row.JSON` is `{"seq":…,"id":…,"rev":…,"deleted":…,"doc":…}`,
`doc` present only under `--include-docs`; `--json` therefore emits one change
per line, which is the whole machine-readable contract.

**Error cases**, all `Usagef`, so exit 2:

| Case | Sentence |
|---|---|
| Path is not a database | `<path> is a <kind>; tail takes a database path.` |
| Path is a partition | `CouchDB has no partition-scoped changes feed; tail /<db> reads the whole database.` |
| `--filter` without exactly one `/` | `--filter takes a design document and a filter name, as "app/by_type".` |
| `--heartbeat` given without `--follow` | `--heartbeat only applies to --follow; the normal feed has no idle period to keep alive.` |
| `--limit` given with `--follow` | `--limit does not apply to --follow, which reads until you stop it.` |
| `--limit` or `--heartbeat` negative | `--limit cannot be negative.` / `--heartbeat cannot be negative.` |

## 6. `--replication-url`

CouchDB replication endpoints are URLs the *server* dials. v1.0 hands CouchDB
the address `cdb` itself connected with, which is wrong whenever the two do not
agree: a container published on `localhost:15984` that calls itself
`http://couchdb:5984`, an SSH tunnel, a reverse proxy. v1.0 documents the
symptom as a known limitation; this is the fix. Precedence mirrors `--url`
exactly — the global one-shot flag `--replication-url URL` (beside `--url` on
the cobra root), then `CDB_REPLICATION_URL`, then the profile key
`replication_url`. `connect --replication-url URL` sets it for the session and
`--save` persists it. Unset means "use the client URL", which is v1.0
behaviour.

Validated once, where it enters `couch.Config`:

| Case | Sentence |
|---|---|
| Not an absolute http(s) URL | `The replication URL must be an absolute http or https URL.` |
| Carries userinfo | `The replication URL must not contain a user name or password; cdb sends the profile's credentials in the replication document instead.` |
| Carries a query or fragment | `The replication URL must be a bare server address, with no query string or fragment.` |

A trailing `/` is trimmed. It is a *server* address, not a database address:
`ReplicationEndpoint(db)` appends `"/" + path.Encode(db)`. Consumers are
`replicate`, and `cp` between two databases on the connected server, both
through `replicate.ResolveEndpoint` → `Client.ReplicationEndpoint`. A full
`http(s)` endpoint typed on the command line is unaffected.

`info /` gains a `replication url` row, shown only when it differs from the
client URL, so the common case stays uncluttered; validation guarantees the
value is credential-free, so it is safe to render. `replicate`'s `Details`
prose gains one sentence: `If the server cannot reach the address cdb connected
with, set --replication-url (or replication_url in the profile) to the address
the server knows itself by.` The README's "Replication and same-server jobs"
section is updated to match.

## 7. `backup --tombstones` and `restore`

```
backup <db-path> <file> [--resume] [--since SEQ] [--batch N] [--tombstones]
```

Without `--tombstones` nothing changes: deleted rows in the changes feed are
skipped, as in v1.0. With it, a deleted row is no longer skipped; its leaf
revisions go into the same `_bulk_get?revs=true` request as live documents, and
CouchDB returns `{"_id":…,"_rev":…,"_deleted":true,"_revisions":{…}}`, written
as an ordinary `doc` record. Tombstones carry no `_attachments`, so
`splitAttachments` finds none and no `att` record follows them.

The header records `"tombstones":true`. The footer gains `"deleted":N`,
counting tombstone records; `docs` continues to count *every* `doc` record,
tombstones included, so `docs - deleted` is the number of live revisions. The
completion message gains the count when it is non-zero: `Wrote 412 document(s)
(37 of them deletions), 6 attachment(s) and 1.2 MB from "mydb" to mydb.cdb.gz
(sequence 941-g1AAA…).`

`--resume` must not mix modes. `backup.Resume` gains `Deleted int64` and
`Tombstones bool` (read from the header in the file's first member), and
`backup` refuses a mismatch with `<file> was written without tombstones; resume
it without --tombstones, or start a new dump.` — or the converse, `<file> was
written with tombstones; resume it with --tombstones, or start a new dump.`
Both `Usagef`, exit 2.

**Restore.** A `doc` record carrying `_deleted:true` needs no special write
path: `_bulk_docs` with `new_edits=false` already stores it with its supplied
`_rev` and `_revisions`, which is exactly what makes the deletion replicate
onward. Two changes: tombstones are counted separately and reported (`Restored
412 document(s) (37 of them deletions), 6 attachment(s) and 1.2 MB into
"mydb".`); and an `att` record following a tombstone is a corrupt dump, caught
explicitly with `restore: <file>: attachment "<name>" follows the deletion of
"<id>", which can hold no attachments.` `prepareTarget` is unchanged —
`info.DocCount` excludes deleted documents, so `--merge` still means what it
meant. The README's "carries no deletion tombstones" paragraph is rewritten
around the flag, keeping the point that a conflicted document is dumped once
per leaf revision.

## 8. `resolve` diff view

```
resolve <doc-path> [--keep REV] [--diff-full]
```

Before the chooser prompt, `resolve` shows how each revision differs from the
current winner, instead of an 80-character preview of each body.

`DiffRevisions(winner, other, rev)` compares the two decoded objects at the top
level only. Fields whose names begin with `_` are ignored, except `_deleted`
and `_attachments`; `_attachments` is compared by attachment count and rendered
as `N attachment(s)` on each side. A field present only in `other` is
`ChangeAdded`; only in the winner, `ChangeRemoved`; in both with different
compact JSON, `ChangeChanged` — comparison is on `json.Marshal` of the decoded
value, so key order and whitespace do not register. Values are summarised as
compact JSON truncated on a rune boundary to 40 runes with a trailing `…`.
Changes are sorted by field name, so output is stable.

`Summary()` renders one line, semicolon-separated, in the order changed, added,
removed — `changed: title "The Shawshank Re…" → "Shawshank Redemption"; added:
rating 9.3; removed: draft`. An empty `Changes` renders as `no differences from
the current revision`, which is what the winner's own entry always shows. A
revision whose body is not a JSON object (CouchDB will not produce one, but a
hand-written `_bulk_docs` can) renders as `this revision is not a JSON object`
and stays selectable. The chooser becomes:

```
1) 3-a1b2c3 (current)
   no differences from the current revision
2) 3-d4e5f6 (conflict)
   changed: year 1994 → 1995; added: rating 9.3
3) 3-9a8b7c (conflict)
   removed: draft
Keep which revision? [1-3]
```

`--diff-full` replaces each summary line with that revision's complete
pretty-printed JSON, indented two spaces; the prompt is unchanged.
`--diff-full` with `--keep` is a usage error: `--diff-full shows the revisions
before you choose one, so it has no effect with --keep.` Non-interactive
without `--keep` is unchanged from v1.0. `conflicts` is unchanged: it lists
documents and revisions, and keeps its 80-character summary column.

## 9. Partition-scoped paths

After `/db/_partition/<key>`, `path.Resolve` parses the remaining segments by
the same rules it uses after `/db`, with two differences: a document id gets
the partition prefix, and a design document alone is refused. In every form
below `Target.Partition` is the key, `Target.Database` is the database, and
`Target.Path` keeps the `_partition` form as typed (canonicalised), because
that is the text error messages and paging hints print.

| Path | Kind | `DocID` | Request base |
|---|---|---|---|
| `/db/_partition/p1` | `KindPartition` | — | `/db/_partition/p1` |
| `/db/_partition/p1/doc1` | `KindDocument` | `p1:doc1` | `/db/p1:doc1` |
| `/db/_partition/p1/doc1/photo.jpg` | `KindAttachment` | `p1:doc1` | `/db/p1:doc1/photo.jpg` |
| `/db/_partition/p1/_design/app/_view/by_date` | `KindView` | `_design/app` | `/db/_partition/p1/_design/app/_view/by_date` |

The document rule is CouchDB's own convention: a document in partition `p1` has
an id of the form `p1:<rest>`. `Resolve` prefixes the key and a colon, **unless
the segment already begins with `<key>:`**, in which case it is used as-is — so
`/db/_partition/p1/doc1` and `/db/_partition/p1/p1:doc1` name the same
document, and a path built by pasting an id straight out of `ls` works. There
is no partition-scoped document endpoint in CouchDB; the partition lives in the
id, which is why `DocID` carries it and the request base does not. Design
documents are not partition-scoped, so `/db/_partition/p1/_design/app` with
nothing after it is refused: `invalid path "…": a design document is not
partition-scoped; use /db/_design/app, or add /_view/<name> to run the view
against the partition`. Anything after `_view/<name>` is `path has too many
segments`, as today.

Command behaviour, most of which falls out of `Target` already carrying
`Partition`. `cd`'s `verifyTarget` treats a partitioned document, attachment or
view as the unpartitioned one: it reads `DocID`, and for a view checks the name
against the design document's `views`, reading that design document at
`/db/_design/app` rather than through the partition. `ls` needs no change —
`lsDatabase` already passes `Partition` into `AllDocsOptions`, producing
`/db/_partition/p1/_all_docs`; its `--start` takes a raw document id, so `p1:m`,
not `m`. `cat`, `put`, `rm`, `edit`, `attach` and `fetch` are unchanged: they
use `DocID`, which now carries the prefix. `FindOptions.Partition` and
`ViewOptions.Partition` are already wired to `/db/_partition/{key}/_find`,
`/_explain` and `…/_design/…/_view/…`, so the grammar change is what makes
`find` and `query` reachable from a path argument as well as from `cd`.
Completion gains one case in `CompletePath`: under a `KindPartition` directory
it already lists ids through the partitioned `_all_docs`, and those come back
fully qualified (`p1:doc1`), so the candidate's `Value` and `Display` are both
the id with the `<key>:` prefix stripped; after a partitioned document segment
it offers `_design`, then `_view`, then view names, reusing `viewCandidates`.

`tail` is the one command that refuses a partition path (§5).

## 10. Small behaviours

### 10.1 `ls --all --start`

Already fixed on `main` in commit 0033ad8 and pinned by
`internal/command/ls_all_start_test.go`. v1.1 adds one case there for a
partition path, so `ls /db/_partition/p1 --all --start p1:m` streams from the
given id. No production change is expected; if the case fails, the fix is to
pass `StartKeyDocID` through the partitioned branch too.

### 10.2 `find` on a document path

`splitFindArgs` resolves its path argument and then uses only
`Target.Database`, so `find /mydb/doc1 '{"a":1}'` silently queries the whole
database. After resolving, `find` rejects every kind but `KindDatabase` and
`KindPartition`: `/mydb/doc1 is a document; find queries a database or a
partition. Use "cat /mydb/doc1" to read one document.` (`Usagef`, exit 2). The
existing "find needs a database" sentence for the server root is unchanged.

### 10.3 Completion of `--fields=name` and comma lists

Two independent gaps on the path from keystroke to `CompleteFields`.
`Shell.CompleteLine` sends any word starting with `-` to the flag-name branch,
so `--fields=na` never reaches the command's `Complete` and matches no flag
name either. A case is added before that branch: when the word matches
`--<name>=<value>` and `<name>` is a declared flag of the command that takes a
value, it calls `c.Complete(ctx, sess, append(settled, "--"+name), value)` and
prefixes every returned `Candidate.Value` with `--<name>=`, leaving `Display`
alone so the menu still shows bare names.

Separately, `--fields` and `--sort` are `StringSlice` flags, so
`--fields title,ye` is one word. `CompleteFields` splits `cur` at the last
comma: everything up to and including it is a fixed prefix, the remainder is
matched against the sampled field names, and each candidate's `Value` is
prefix + field. With no comma, behaviour is what it is today. The two compose,
so `--fields=title,ye` completes.

## 11. Config and environment additions

```toml
[profiles.local]
url = "http://localhost:15984"
replication_url = "http://couchdb:5984"   # new in 1.1
auth = "session"
username = "admin"
```

| Name | Kind | Meaning |
|---|---|---|
| `replication_url` | profile key | Address the server should use to reach itself. Optional; defaults to `url`. |
| `CDB_REPLICATION_URL` | environment | Overrides the profile key; `--replication-url` overrides it in turn. |
| `CDB_TEST_JWT_SECRET` | environment, tests only | HS256 signing secret shared with the CouchDB under test. Its presence, with `CDB_TEST_URL`, un-skips the live JWT test. |

`replication_url` is a plain address and never a secret, so it lives in
`config.toml` beside `url` and is shown by `profiles list` and `info`. No new
keyring entry, no new key in `[output]` or `[shell]`. The README's
configuration and global-flag tables gain `--replication-url`; the environment
list gains `CDB_REPLICATION_URL`; the development section gains the JWT setup
from §13.

## 12. Dump format 1.1

```
{"kind":"header","version":"1.1","db":"mydb","server":"3.5.2",
 "started":"2026-09-08T10:00:00Z","partitioned":false,"tombstones":true}
{"kind":"doc","doc":{…live document, _rev and _revisions, no _attachments…}}
{"kind":"doc","doc":{"_id":"gone","_rev":"3-c0ffee","_deleted":true,
                     "_revisions":{"start":3,"ids":["c0ffee","…","…"]}}}
{"kind":"att","id":"doc1","rev":"2-abc","name":"photo.jpg",
 "content_type":"image/jpeg","length":12345}<12345 raw bytes>\n
{"kind":"checkpoint","seq":"…"}
{"kind":"footer","docs":412,"deleted":37,"attachments":6,"last_seq":"…"}
```

Changes from 1.0, all additive: `header.version` (string, `"1.1"`, written by
every 1.1 backup whether or not `--tombstones` was given); `header.tombstones`
(bool, true only under `--tombstones` — it is what tells a reader whether the
absence of a tombstone means "never deleted" or "deletions were not
recorded"); and `footer.deleted` (int64, the number of `doc` records carrying
`_deleted:true`; absent means zero). A tombstone is an ordinary `doc` record —
no new `kind`, so every reader that walks `doc` records already handles it.

Compatibility rules. A missing `header.version` means `"1.0"`; `backup.Reader`
and `backup.Scan` accept `"1.0"` and `"1.1"`. Any other value is refused, by
`restore` and by `backup --resume`, with `<file> was written by a newer cdb
(dump format <v>); upgrade cdb to read it.` (`Usagef`, exit 2). Unknown
*fields* inside a known record are ignored, as today, so a 1.2 header read by a
1.1 binary is a version refusal and nothing else. A 1.0 binary reading a 1.1
dump works in practice — it ignores the new header fields, restores tombstone
`doc` records correctly through `new_edits=false`, and ignores `footer.deleted`
— but that is observed, not promised; no future format change is constrained by
it.

Struct changes: `backup.Header` gains
``Version string `json:"version,omitempty"` `` and
``Tombstones bool `json:"tombstones,omitempty"` ``; `backup.Footer` gains
``Deleted int64 `json:"deleted,omitempty"` ``; `backup.Resume` gains
`Deleted int64` and `Tombstones bool`.

## 13. Testing

Unit tests against the `couchtest` route stub, in the style each package
already uses. `couchtest.Server.On` hands the test a raw `http.HandlerFunc`, so
a continuous feed is stubbed with an `http.Flusher` and no stub change is
needed.

`internal/couch` covers `Changes` for each option; `ChangesFollow` against a
handler that writes newline-delimited changes, a blank heartbeat line, the
trailing `last_seq` line, and a body cut short mid-stream; and
`ReplicationEndpoint` with and without `ReplicationURL`, asserting the
credential object is untouched. `internal/command` covers `tail` normal-feed
rows and hint; `tail --follow` reconnecting from the last seen sequence on the
documented backoff, driven through the `backoffSleep` var so the test does not
sleep; each `tail` usage error; `tail` cancellation surfacing
`context.Canceled`; `backup --tombstones` writing tombstone records and a
`deleted` footer; `--resume` refusing a mode mismatch both ways; `restore` of a
tombstone dump, asserting the exact `_bulk_docs` body carries `_deleted:true`
and `new_edits:false`; `DiffRevisions` table-driven over added, removed,
changed, underscore, `_attachments` and non-object cases; the chooser with and
without `--diff-full`; `find` on a document path; and `ls --all --start` on a
partition. `internal/path` takes one case per row of §9's table plus the
`p1:doc1` idempotence rule and the design-document refusal; `internal/shell`,
`--fields=na`, `--fields title,ye` and `--fields=title,ye` all reaching
`CompleteFields` with the right `cur` and returning correctly prefixed values;
`internal/backup`, a round-trip of a dump containing tombstones, `Scan`
reporting `Deleted` and `Tombstones`, a 1.0 dump (no `version`) read by the 1.1
reader, and a `"1.2"` header refused; `internal/render`, a `Live` stream
emitting each row before the next is produced and not paging.

Integration tests stay gated on `CDB_TEST_URL` and run in CI against the
`couchdb:3.5` service container: `tail --follow` against a database written to
concurrently, and a `backup --tombstones` / `restore` round-trip that deletes a
document, restores into a fresh database, and replicates that onward to prove
the deletion carries.

**Live JWT test.** Deferred in v1.0 because CouchDB 3.5's default
`chttpd_auth/authentication_handlers` has no JWT handler, so a bearer token is
ignored and the test would assert nothing. CI declares
`CDB_TEST_JWT_SECRET: ci-jwt-secret` at job level and gains one step before the
test step:

```yaml
- name: Enable the JWT handler
  run: |
    b64=$(printf %s "$CDB_TEST_JWT_SECRET" | base64 | tr -d '\n')
    curl -fsS -X PUT -H 'Content-Type: application/json' \
      "http://admin:password@localhost:5984/_node/_local/_config/jwt_keys/hmac:_default" \
      -d "\"$b64\""
    curl -fsS -X PUT -H 'Content-Type: application/json' \
      "http://admin:password@localhost:5984/_node/_local/_config/chttpd_auth/authentication_handlers" \
      -d '"{chttpd_auth, jwt_authentication_handler}, {chttpd_auth, cookie_authentication_handler}, {chttpd_auth, default_authentication_handler}"'
```

The cookie and default handlers are kept, so every existing session-auth test
still passes. `internal/command/integration_jwt_test.go` skips unless both
`CDB_TEST_URL` and `CDB_TEST_JWT_SECRET` are set. It mints an HS256 token with
header `{"alg":"HS256","typ":"JWT"}` and claims
`{"sub":"admin","_couchdb.roles":["_admin"],"exp":<now+300>}`, signs it with
the raw secret, runs `connect <url>` with `auth = "jwt"` and the token as the
secret, and asserts the session reports `admin` with the `_admin` role and that
`ls /` succeeds. A second case asserts an expired token gives exit 3 and the
login-failure sentence, not a 500. `CDB_KEYRING_BACKEND=file` still applies, so
no real keychain is touched.

## 14. Compatibility

Version 1.1.0, reported by `cdb version` from the existing ldflags. No command
is removed or renamed; no flag changes meaning; no default changes. Every v1.0
invocation produces v1.0 output, with two visible additions: `info /` may show
a `replication url` row, and `resolve`'s chooser shows diffs instead of body
previews. `config.toml` files written by v1.0 load unchanged, `replication_url`
being optional, and dumps written by v1.0 restore under v1.1 (§12).
`couch.Changes` changes signature, but it is an internal package with one
caller in the tree and nothing outside `internal/` can depend on it. CHANGELOG
gains a `[1.1.0]` section, and the two "Known limitations" bullets about
tombstones and about an unreachable same-server replication endpoint move into
"Added" as the flags that address them.

## 15. Out of scope for 1.1

The Bubble Tea TUI; cluster setup, `_config` editing, user management,
`_active_tasks` and compaction; Nouveau or Clouseau search; proxy
authentication; Cloudant IAM; multi-stage shell pipelines; CouchDB 2.x. Also
deliberately excluded, though adjacent: a partition-scoped `tail` (CouchDB does
not offer one); `_changes` filters other than `ddoc/name` (`_doc_ids`,
`_selector`, `_view`); a diff between two arbitrary documents or two databases,
`resolve`'s diff being against the winner of one document's conflicts;
nested-field diffs, top level only; `conflicts --diff`; and automatic conflict
merging — `resolve` still keeps one revision whole.
